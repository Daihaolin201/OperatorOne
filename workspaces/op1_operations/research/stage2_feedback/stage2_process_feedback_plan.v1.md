# Stage2 Capability Plan — Process feedback

Generated by: `op1_operations`
Date: 2026-03-05

## 1) Goal and boundary

**Goal:** Build a complete feedback processing capability that converts raw feedback signals into prioritized, actionable product improvements tied to conversion economics.

**Business objective alignment:** Improve progress to first `$100 MRR` by reducing friction observed in traffic→signup→paid funnel and by increasing objection-resolution win rate.

**Boundary for this stage:**
- Focus on feedback processing system and outputs (not full product rebuild).
- Support simulated inputs today, preserve adapter path for live inputs later.

## 3) External benchmark principles used

Design incorporates patterns consistently recommended in leading docs/practices:
- **Prompted + unprompted feedback collection** and weighting by customer segment and stakes.
- **Voice-of-Customer (VoC) program**: multi-source ingestion, text analytics/sentiment, trend detection.
- **Contextual collection and routing tags** to speed triage (feature-area tags).
- **Event-based data model** with strict fields and enrichment properties.
- **Prioritization frameworks**: RICE for impact/effort tradeoff and Kano for feature class.
- **Action-first loop**: route insights to owners, track closure, and report back to requesters.

## 4) Full Stage2 capability model (no phased split)

### Capability A — Feedback source adapters
Implement adapters for all available feedback signals:
- sales outreach replies
- conversion objections
- manual notes/interviews (CSV/JSON drop)
- product runtime feedback endpoint (future live adapter)
- optional social/review source adapter placeholders

Output:
- `research/stage2_feedback/raw_feedback_events.latest.jsonl`

### Capability B — Canonical feedback contract
Define strict schema for each feedback unit:
- `feedback_id`, `source_adapter`, `source_ref`, `feedback_time`
- `actor_id` (`lead_id`/`user_id`/`anonymous_id`)
- `channel`, `raw_text`, `normalized_text`, `language`
- `feedback_type` (`bug|feature_request|objection|praise|confusion|churn_risk|pricing|other`)
- `topic`, `subtopic`, `journey_stage`
- `severity`, `urgency`, `sentiment`
- `evidence_weight`, `confidence`
- attribution keys (`campaign_id`, `event_source`, `event_medium`)

Output:
- `contracts/feedback_taxonomy.v1.yaml`
- `contracts/feedback_contract.v1.json`

### Capability C — Taxonomy governance
Standardize taxonomy and avoid drift:
- top-level domains: onboarding, pricing, trust, integration, performance, support, billing
- subtopic dictionary and synonym mapping
- prohibited free-text tags in structured output

Output:
- `contracts/feedback_taxonomy.v1.yaml`
- `references/feedback_tagging_guide.md`

### Capability D — Normalization & deduplication
- normalize text, remove boilerplate, unify language/casing
- semantic and rule-based duplicate detection
- keep one canonical feedback item with `duplicate_count`

Output:
- `research/stage2_feedback/feedback_dedup.latest.json`

### Capability E — Clustering & theme detection
- cluster similar feedback into themes
- maintain stable theme IDs over reruns
- detect emerging themes vs recurring themes

Output:
- `research/stage2_feedback/theme_clusters.latest.json`

### Capability F — Quality and trust scoring
Score each item:
- source reliability
- customer fit (ICP tier / lead quality)
- severity and frequency
- recency decay
- evidence confidence

Output:
- `research/stage2_feedback/feedback_scored.latest.jsonl`

### Capability G — Prioritization engine
Use weighted scoring for action queue:
- base formula: `Priority = (Reach * Impact * Confidence * EvidenceWeight) / Effort`
- include revenue leverage and funnel stage impact
- classify with Kano labels for context (basic/performance/delighter)

Output:
- `research/stage2_feedback/feedback_priority_queue.latest.json`

### Capability H — Insight brief generator
For top themes, generate execution-ready briefs:
- problem statement
- affected segment and frequency
- evidence excerpts
- hypothesis
- recommended experiment
- expected KPI movement

Output:
- `research/stage2_feedback/insight_briefs.latest.md`

### Capability I — Closed-loop tracker
Track lifecycle per feedback item:
- `new -> triaged -> accepted -> planned -> shipped -> verified -> notified`
- include SLA timestamps and owner

Output:
- `research/stage2_feedback/feedback_loop_status.latest.json`

### Capability J — Feedback-to-KPI linkage
Link themes to Stage1 metrics:
- map each theme to impacted funnel step
- estimate opportunity size (`delta signup rate`, `delta paid rate`, `delta MRR`)

Output:
- `research/stage2_feedback/impact_model.latest.json`

### Capability K — Alerts and escalation
Alerts for high-risk signals:
- security/privacy/trust blockers
- sudden spike in churn-risk or unsubscribe reason
- repeated blocker unresolved beyond SLA

Output:
- `research/stage2_feedback/feedback_alerts.latest.json`

### Capability L — Data quality controls
- schema completeness
- duplicate ratio
- stale source detection
- taxonomy coverage and unknown-tag rate

Output:
- `research/stage2_feedback/feedback_data_quality.latest.json`

### Capability M — Reproducibility controls
- deterministic runs with `STAGE2_AS_OF`
- hash baseline checks
- strict mode for delivery readiness

Output:
- `research/stage2_feedback/reproducibility_report.latest.json`

### Capability N — Scoreboard & weekly operating snapshot
Create operations-facing digest:
- top themes by weighted impact
- objection trend shifts
- decision throughput and closure rate
- next actions

Output:
- `research/stage2_feedback/stage2_feedback_scoreboard.latest.json`
- `research/stage2_feedback/stage2_feedback_scoreboard.latest.md`
- `research/stage2_feedback/weekly_feedback_snapshot.latest.md`

### Capability O — Handoff outputs for product iteration
Produce structured outputs for Stage3 (iterate on product):
- prioritized problem backlog
- recommended experiments and owners
- traceability back to evidence items

Output:
- `handoffs/operations_to_product.json`
- `handoffs/operations_to_marketing.json` (messaging gaps)
- `handoffs/operations_to_sales.json` (objection playbook updates)

## 6) KPI framework for Stage2 capability health

System KPIs:
- ingestion freshness (hours)
- triage SLA (median hours)
- duplicate compression ratio
- unknown taxonomy tag rate
- reproducibility pass/fail

Outcome KPIs:
- top-3 theme resolution rate
- objection-to-conversion recovery rate
- feedback-to-shipped cycle time
- funnel lift linked to resolved themes

---

## 7) Acceptance criteria for "complete Stage2 capability"

Stage2 is complete only if all conditions hold:
1. Multi-source feedback ingests into one canonical schema.
2. Duplicate and clustering are stable across reruns.
3. Priority queue is deterministic and explainable.
4. Every priority item has traceable evidence references.
5. Closed-loop status is measurable per item and owner.
6. Scoreboard + weekly snapshot auto-generated.
7. Reproducibility strict mode passes with fixed as-of.
8. Handoff payloads are consumable by product/marketing/sales.

---

## 8) Delivery risks and controls

Major risks:
- feedback noise overwhelms signal
- overfitting to loud outliers
- taxonomy drift across teams
- non-deterministic scoring leading to trust loss

Controls:
- confidence weighting + segment weighting
- explicit stakes/volume/repetition logic
- strict taxonomy dictionary with unknown-tag alerts
- reproducibility baseline + strict mode checks
